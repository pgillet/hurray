# TODO

- Data-driven layout: the reference implementation may repack/convert a tensor to a more optimized layout by introspecting the tensor data itself or the attached tensor statistics
- Redis module: use Hurray as the native tensor type for a Redis module (storage + serving, format-aware, no inference execution — narrower and more useful than the abandoned RedisAI approach)
- Cookbook: a collection of recipes demonstrating common Hurray usage patterns in Rust and Python (e.g., creating and reading tensors, quantized inference, zero-copy interop with NumPy/PyTorch, IPC exchange)
- Tensor view / reshape annotation (v2 candidate): a mechanism for a descriptor to reference an existing buffer with a different shape, strides, or rank (zero-copy reshape, slice, transpose, broadcast). Key design constraint: conflicts with the "no back-references" streaming rule — likely restricted to file format and in-process buffer protocol, not the streaming wire format. Would subsume compound element types as a special case (rank r-1 view with named components). Deferred from v1; revisit when streaming model constraints are better understood.
- hurray-python display: implement `__repr__` and `__str__` for `hurray.Tensor` (and `hurray.SparseTensor`) to display array contents and metadata on standard output, following NumPy/PyTorch conventions.
- CSF (Compressed Sparse Fiber) layout: generalization of CSR/CSC to arbitrary rank. Each level adds a (ptr, idx) pair, giving `rank` levels total. Used in tensor algebra compilers (TACO). Would be the natural higher-rank complement to COO for structured sparsity patterns in ML workloads (attention masks, activation tensors). Prerequisite: spec section in `docs/spec/layouts/csf.md` + layout tag assignment.
- hurray-compute crate (re-evaluate when a second language binding exists): a Rust crate sitting between hurray-core and the binding layers, providing tensor construction kernels (zeros, ones, full, arange, linspace), type-conversion fills, and potentially SIMD/rayon-accelerated operations. Would eliminate duplication across hurray-python, future hurray-js/java bindings. Not warranted today (YAGNI — hurray-python is the only consumer); revisit when a second binding is added or when a non-trivial shared kernel emerges.
- Python Array API conformance suite (array-api-tests): add to CI once a first batch of element-wise ops and `astype` land. Running it earlier produces ~80% expected failures (missing computational functions) and adds noise without signal. Trigger: when `hurray.add`, `hurray.multiply`, and `Tensor.astype` are implemented. Setup: `pip install array-api-tests && pytest array_api_tests/ --array-module=hurray`.
